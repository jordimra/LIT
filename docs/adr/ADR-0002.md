# ADR 0002: Eliminación conceptual del Staging Area (Index)

## Contexto
En Git, existe un modelo de tres áreas para gestionar los cambios: el Directorio de Trabajo (Working Directory), el Área de Preparación (Staging Area o Index) y el Historial (Repository/Commits). Esto requiere que los desarrolladores realicen un proceso en dos pasos (`git add` seguido de `git commit`) para guardar sus cambios.

Durante el diseño de la entidad `Workspace` para el Modelo de Dominio de LIT, es necesario definir cómo se gestionan los archivos que están siendo modificados antes de convertirse en un `Snapshot`.

## Problema
El concepto de Staging Area es una de las mayores barreras de entrada y fuentes de confusión para los desarrolladores que aprenden Git. A menudo se preguntan por qué sus cambios no se guardaron si hicieron `git commit` pero olvidaron hacer `git add`. Esto viola los principios de LIT de "Simplicidad antes que potencia" y "Nunca sorprender al usuario".

## Alternativas
1. **Mantener el modelo de tres áreas (Git clásico)**: 
   - Exponer conceptualmente un "Área de Preparación" en LIT.
   - *Pros*: Máxima flexibilidad, permite commits parciales fácilmente.
   - *Contras*: Mantiene la complejidad cognitiva que LIT intenta resolver.
2. **Eliminar conceptualmente el Staging Area (Modelo de dos áreas)**:
   - Pasar directamente de `Workspace` a `Snapshot`. El Workspace representa el estado actual, y al hacer un guardado (`lit save`), todo el estado rastreado del Workspace pasa a ser un Snapshot.
   - *Pros*: Simplifica drásticamente el modelo mental a "Lo que tengo" vs "Lo que he guardado". Alineación perfecta con el principio de simplicidad.
   - *Contras*: Dificulta hacer guardados parciales de archivos modificados (aunque la CLI podría solventarlo con comandos específicos, el modelo base no lo expone).

## Decisión
Se elige la **Alternativa 2: Eliminar conceptualmente el Staging Area**.
En el modelo de dominio de LIT, el `Workspace` es el único lugar donde residen los cambios no guardados. No existe un concepto intermedio. Un `Snapshot` captura automáticamente el estado actual del `Workspace`.
A nivel de infraestructura (Git Adapter), LIT ejecutará implícitamente la adición al índice antes de realizar el commit en Git, ocultando este detalle al usuario.

## Consecuencias
- La definición de la entidad `Workspace` se simplifica.
- Las operaciones principales de la API no requerirán pasos intermedios de "preparación".
- Para permitir flexibilidad avanzada en el futuro (como guardados de líneas específicas), LIT deberá abstraerlo en operaciones de la interfaz sin introducir el concepto de un área intermedia persistente en el modelo mental.
