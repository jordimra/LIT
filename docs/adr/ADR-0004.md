# ADR 0004: Estrategia de Interacción con Git (JGit vs Git CLI)

## Contexto
Durante la Fase 7 (Adaptador Git), necesitamos conectar el núcleo de LIT (el `LitService`) con repositorios de Git reales. Existen dos aproximaciones principales en el ecosistema Java para interactuar con repositorios Git: usar una librería nativa de Java (como JGit) o invocar al ejecutable de Git nativo mediante el sistema operativo (Git CLI a través de `ProcessBuilder`).

## Problema
Debemos asegurar la máxima compatibilidad, estabilidad y facilidad de mantenimiento. Si elegimos una estrategia que no soporta todas las características de Git o que es inconsistente con el entorno del usuario, LIT no cumplirá su promesa de transparencia y fiabilidad ("Nunca sorprender al usuario").

## Alternativas

### 1. JGit (Librería nativa de Java)
- *Pros*:
  - Integración nativa sin dependencias externas del sistema.
  - Mayor velocidad en ciertas operaciones al no requerir creación de procesos.
  - Multiplataforma por definición.
- *Contras*:
  - No siempre está alineado al 100% con la implementación oficial en C (Git CLI).
  - Problemas frecuentes con configuraciones SSH complejas (agentes, llaves específicas) y asistentes de credenciales del sistema operativo.
  - No ejecuta los "hooks" de Git automáticamente, lo que puede romper los flujos de trabajo de los equipos.

### 2. Git CLI (Ejecución de procesos, `ProcessBuilder`)
- *Pros*:
  - 100% de compatibilidad con la instalación de Git del usuario.
  - Soporta de forma nativa todo el ecosistema de Git: credenciales, hooks, archivos de configuración locales/globales, y firmas GPG.
  - Delegar el trabajo pesado a una herramienta madura.
- *Contras*:
  - Depende de que Git esté instalado y en el PATH del sistema operativo.
  - Invocación de procesos (overhead ligero).
  - Posibles problemas con la codificación de caracteres en las salidas de la terminal (especialmente en Windows).

## Decisión
Se elige la **Alternativa 2: Git CLI (Ejecución de procesos)**.
LIT abstraerá la complejidad de los comandos, pero internamente usará `java.lang.ProcessBuilder` (o similar) para ejecutar binarios de Git. Esta decisión prioriza el principio de "Nunca sorprender al usuario", ya que respeta su configuración SSH, sus credenciales guardadas y sus hooks de pre-commit, aspectos cruciales para la adopción en proyectos reales.

## Consecuencias
- El sistema requerirá que el ejecutable `git` esté disponible en el PATH del usuario.
- Será necesario implementar un enlazador robusto (un executor) capaz de gestionar correctamente `stdout`, `stderr`, y códigos de salida para mapearlos a la jerarquía de excepciones de LIT (`LitException`, `GitAdapterException`).
- Debemos ser muy cuidadosos con el parseo de la salida de los comandos Git; priorizaremos el uso de formatos predecibles (por ejemplo, `git status --porcelain`) para evitar roturas por internacionalización.
